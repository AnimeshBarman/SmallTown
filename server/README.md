# Backend development

## Install and test

Use Python 3.10 or newer:

```sh
python -m venv SmallTownENV
SmallTownENV/bin/pip install -r requirements.txt
SmallTownENV/bin/python -m unittest discover -s tests -v
```

The test suite uses Python's built-in `unittest` runner and does not connect to
PostgreSQL or Redis. Runtime configuration still comes from `server/.env`.

## Database migrations

The API no longer creates tables or alters the database when it starts. Apply
schema changes explicitly from this directory:

```sh
SmallTownENV/bin/alembic upgrade head
```

The first migration adopts an existing SmallTown schema as well as bootstrapping
a new database. It uses idempotent table/index creation and adds the compatibility
columns that were previously applied at startup. It does not delete data. Its
downgrade is intentionally a no-op because it cannot know which pre-existing
objects or records are safe to remove.

Before applying it to a hosted database, take a database backup and review the
target connection. Do not use `alembic stamp` as a substitute: run `upgrade head`
so any missing compatibility changes are applied.

GitHub Actions runs the unit tests and applies this migration to a disposable
PostGIS database, then replays the adoption revision without its version marker
to check that the compatibility path is safe to repeat.

For each later schema change, create and review a new revision:

```sh
SmallTownENV/bin/alembic revision --autogenerate -m "describe the schema change"
```

Autogenerated migrations must be inspected and tested before deployment. Apply
them with `alembic upgrade head`; do not put schema DDL back into application
startup code.
